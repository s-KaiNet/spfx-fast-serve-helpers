# Source layout

Data flow: **config → project model → generated artifacts → Vite server → browser runtime**
(see [docs/vite/HANDOFF.md §8](../docs/vite/HANDOFF.md)).

Entry points:

- `cli.ts`: `fast-serve` bin (thin; process wiring only).
- `runCli.ts`: argument parsing (testable, no `process` access).
- `devServer.ts`: `startDevServer()`: SPFx version check → options + project model → `vite.createServer()` (no user `vite.config`). Startup failures (port in use, certificate, no web parts) close the server and are rethrown as readable messages; the CLI exits with code 1.
- `plugins.ts`: composes the feature modules' Vite plugins.
- `context.ts`: `ServeContext` (root, resolved options, project model, logger) passed to every module.

Modules:

| Folder | Owns |
|---|---|
| `config/` | options (`port`, `pageUrl`, `locale`, `serveConfiguration`): CLI flags > `config/fast-serve.json` > `config/serve.json` > defaults; selects the `serve.json` serve configuration (`default` unless named; an unknown name is an error) and its page (`pageUrl` option > configuration > `default` > `initialPage`) |
| `project/` | SPFx project facts, plain Node, **no Vite imports**: config.json bundles → components (web parts and extensions; other component types are skipped with a warning), manifests, `serve.json` (`serveConfigurations.ts`: validated `customActions` / `fieldCustomizers` / `formCustomizer`), package.json, serve.json, loc files, SPFx libraries in node_modules, `config.json` `externals` (`configExternals.ts`: URLs and local files with `globalName`/`globalDependencies`, validated like heft; SPFx libraries win over an external with the same name), lib→src mapping, `tsconfig.json` read once through `extends` (`tsconfig.ts`: the chain of files and their `compilerOptions`), its `paths`/`baseUrl` (`tsconfigPaths.ts`, tsc's matching rules) and merged compiler options. Cached; `invalidate(file)` returns `'model'` or `'tsconfig'`. `spfxVersion.ts`: installed SPFx version (`@microsoft/sp-core-library`, then `spfx-heft-plugins`) checked against this package's `major.minor` |
| `manifests/` | `GET /temp/build/manifests.js` (debug manifests); relative `./` icon paths (web part `preconfiguredEntries`, command set `items`) → absolute dev server URLs (`iconUrls.ts`) |
| `loader/` | AMD shim per bundle (`/@spfx/bundle/<bundle>.js`) + generated ESM entry (`/@spfx/entry/<bundle>`) with the Fast Refresh preamble; `optimizeDeps.entries`. `serverErrors.ts`: records the last server error (error-handling middleware) and serves `/@spfx/status` (`{ error, fileRevision }`); the shim uses it to show compile errors in the web part and to reload the page after the next file change when a bundle failed to load |
| `externals/` | SPFx library facades (`@microsoft/sp-*` and any package shipping an SPFx library manifest, discovered like SPFx's own externals scan). ESM importers get a top-level-await facade (`loadComponentById(id, version)` via the `libraryLoader` runtime); `require()` importers in pre-bundled deps get a sync facade plus one `await preloadLibraries([...])` per chunk. `config.json` `externals` get the same treatment through `loadExternal(name)` (the component-scoped RequireJS `require`, so the manifest's `paths`/`shim` apply) with ESM/CJS facades and the chunk preload; local files are served from `/@spfx/external/<name>.js`. The debug manifest lists `@microsoft/sp-loader` plus the externals (`type: "path"`, URLs passed through, local files as absolute dev server URLs, `globalName`, `globalDependencies`) |
| `aliases/` | tsconfig `paths`/`baseUrl` for project scripts (`enforce: 'pre'` resolver trying the project model's candidates in order). Vite 8's own `resolve.tsconfigPaths` is not used: it ignores the aliases when the `include` comes from an extended config, which is exactly the SPFx rig setup |
| `assets/` | static-asset typings (`temp/static-asset-ts/**/*.d.ts`, byte-identical to Heft's `static-asset-typings` task) from the project's rig-aware `config/static-asset-typings.json`, written at start and on add, removed on unlink |
| `localization/` | `*Strings` virtual modules from `loc/<locale>.js` or `.ts`: AMD JavaScript is evaluated directly; TypeScript (and JavaScript ES modules) is bundled to CommonJS with Rolldown first, so `export default`, `export =`, typed `define(...)` and imports work. Non-AMD loc files get a warning, because heft copies them to `dist/` as is where RequireJS can't load them |
| `styles/` | SPFx CSS modules naming, `~` Sass imports, theme tokens via the `themedStyles` runtime (resolved once per style insert/hot update, no theme-change watching); `scssTypings/`: Sass typings (`temp/sass-ts/**/*.d.ts`) regenerated on add/change/unlink and once after the startup warmup, with heft's own `SassProcessor` and the project's `config/sass.json` (rig-aware, both resolved from the project) so the output is byte-identical to `heft build` |
| `transforms/` | source-level compatibility for project source: `tsconfig/`: the project's `experimentalDecorators`, `emitDecoratorMetadata`, `useDefineForClassFields`, `target`, `strict`, `strictNullChecks` passed to Oxc as an inline `oxc.tsconfig` (legacy decorators, tsc class field semantics). Never the tsconfig file itself: Oxc's automatic lookup stays off, because the SPFx rig's `importsNotUsedAsValues: "remove"` would keep type-only imports (and oxc-resolver#1357 currently skips the rig's inherited `include`); `DEBUG` / `process.env.NODE_ENV` defines; relative `require('./x.png' / './t.json' / ...)` and `require()` of explicit tsconfig `paths` aliases (not the catch-all `"*"`) → hoisted ESM imports (assets as `?url`, JSON as default, scripts/styles as namespaces); `typeOnlyNames/`: type re-exports without `type` (`export { IFoo } from`, or an imported type exported again) and, with `emitDecoratorMetadata`, imports Oxc keeps because decorator metadata references them (`typeof ILogger === "undefined" ? Object : ILogger`) are checked against the target's runtime exports (Vite's cached transform + es-module-lexer, following `export *`; only project modules and virtual modules, not dependencies), removed from the served code and reported in the terminal and the browser console (re-exports as errors; metadata imports as warnings, since removing them gives tsc's `Object` metadata); `constEnums/`: global `declare const enum`s from `src/**/*.d.ts` (script files and `declare global` blocks, re-scanned on change) used as values in a project module are reported at transform time (terminal + a `console.error` prepended to the module), and a relative import that only resolves to a `.d.ts` fails with a message naming it and its const enums (a normal-order `resolveId`, so it only runs when Vite's resolver found nothing). A named import a dependency doesn't export (a `const enum` such as `IconNames`) can only be seen by the browser when it links modules: the shim adds the hint to the load error |
| `browserErrors/` | browser errors in the terminal, replacing Vite's `server.forwardConsole` (which forwards everything the page logs, SharePoint's own errors included). The `browserErrors` runtime (imported first by every bundle entry, and by the shim before it reports a load failure) sends uncaught errors, unhandled rejections and `console.error` calls (with the call-site stack) over the HMR socket, once per error object; messages fast-serve or Vite already printed (`[fast-serve] `, `[vite]`, or a load failure marked as reported by the server) are skipped. The server prints a report only when a stack frame is a project module on our origin (`/src/...`, not `/node_modules/`, not `/@...`) or the loader (`/@spfx/...`); frames are mapped through the module graph's source maps, trimmed after the last own frame, with a code frame |
| `server/` | HTTPS (Rushstack dev certificate), port/origin, debug URL (`debugUrl.ts`: heft's query, plus `loadSPFX`/`customActions`/`fieldCustomizers`/form customizer parameters without `debug=true` for extension configurations), serve configuration checks against the project's components (`serveConfigurationWarnings.ts`), watch ignores, startup warmup (`warmup.ts`: after the dependency optimizer's first run, transforms the import graph of the bundle entries only, so pre-bundling isn't delayed and unused files aren't transformed; Vite's `server.warmup` is not used; the SCSS typings start after it), React dedupe, project-model changes → full reload (tsconfig changes also invalidate every transformed module, so imports re-resolve; a change of the tsconfig transform options restarts the server) |
| `runtime/` | browser code as TS (own `tsconfig.json`: DOM, no Node), built to `lib/runtime`: `componentShim.ts` and `libraryLoader.ts` (classic scripts, concatenated into the bundle shim, each in its own IIFE with the shared `describeError.ts` helper prepended by `readRuntimeScript()`), `themedStyles.ts` (ES module). `contracts.ts` holds the types shared with Node |
| `utils/` | small helpers (JSONC, paths, error messages, runtime source loading, Vite helpers, `heftProject.ts`: loading Heft packages and rig-aware config files from the project) |

Conventions:

- A feature = one module that returns Vite plugin(s) (each contributes its own Vite config via `config()`), plus its
  browser runtime and tests.
- Plugins added to `optimizeDeps.rolldownOptions.plugins` (pre-bundling and Vite's dependency scan) declare hook
  filters (`{ filter: { id }, handler }`), so Rolldown only calls into JavaScript for matching ids: unfiltered
  hooks run for every module of every dependency and made pre-bundling about twice as slow.
- Tests live next to the code as `*.test.ts` (vitest); fixtures in `test/fixtures/`. Tests are excluded from the build.
- Node code is ESM (`NodeNext`): use `.js` extensions in relative imports.
- Runtime files are served from `lib/runtime/*.js`; when running from sources (tests) the `.ts` file is transpiled on
  the fly (`utils/runtimeSource.ts`).
